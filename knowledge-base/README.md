# Knowledge Base —— 通用知识库（uni-workbench）

uni-workbench 的**第一棵树**：我**知道**什么，也是所有项目的知识总入口。

第二棵树是 `../workbench/`（我**要做**什么，任务流）。领域专属知识（媒体 / 产品 / 职业）沉淀在各自仓库（media-hub / product-hub / career-hub），**不在此重复**。

## 五层结构

```
knowledge-base/
├── 00-Inbox/       所有东西先扔这里 —— 无差别入口，寿命要短
├── 10-Knowledge/   已消化、值得长期保留的知识 —— 本库核心
├── 20-Projects/    项目索引卡 —— 只指向仓库，不复制内容
├── 30-Resources/   外部资料 —— 别人的东西，待加工原料
└── 40-Archive/     暂时不用 —— 冷存放，定期捞回或删除
```

每层的进入规则、收什么不收什么，见各目录下的 `_说明.md`。

## 数据流

```
   随手碰到的东西 ──► 00-Inbox（唯一入口）
                        │ 分流
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
  10-Knowledge    30-Resources      40-Archive
 （我消化的结论）（别人的原文）   （暂时不用）
        ▲                                │
        └──── 定期捞回有价值的 ◄──────────┘

   如果是「要做的事」──► ../workbench/Next/
```

**单向原则**：材料从外向内、从生到熟流动，不反向搬运。原文留在 `30-Resources/`，我的结论写到 `10-Knowledge/` 并回链过去。

「要做的事」不走这一层——在 `00-Inbox/` 判明后直接分流到 `../workbench/`。

## 使用

- **Obsidian**：vault 根设为 `uni-workbench/`（本仓库根）。这样 `knowledge-base/` 与 `workbench/` 两棵树在同一个 vault 里，可以互相双链。
  非知识目录（`engine/`、`skills/`、`docs/`、`scripts/`）已写进 `.obsidian/app.json` 的排除列表，不会被索引。
- **工作台**：`engine/` 成型于双树之前，与新结构**尚未对齐**（详见 `../README.md`）。本库目前由 Obsidian 直接读写，不依赖它。
- **维护规范**：见 `AGENTS.md`（LLM 读写本库的完整 Schema）。

## 现状

**结构先于内容。** 本库交付时是**空库**：此前若有不是本人确认过的知识（AI 生成的合成内容、标着 `demo: true` 的占位条目），一律整体移出本仓库归档，**不作为知识来源**。

现在五层骨架就位、规则明确，从零开始：新内容按规则流入，`10-Knowledge/` 只装真正消化过的东西。
